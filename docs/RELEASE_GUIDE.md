# 发布与官方预览扫描说明

最后核对日期：2026-05-16

这份文档的目标不是解释如何写插件，而是把 **Obsidian 官方审核机器人、预览扫描、正式提交与版本发布之间的关系** 固化到本地，方便后续直接查，不再重复上网整理。

## 先说结论

- 如果你现在的目标是 **反复让官方机器人帮你找问题**，优先使用 **预览扫描**。
- 预览扫描阶段，尽量不要为了每次试错都新增正式版本号。
- **不要**在 `manifest.json` 的 `description` 里写 `Obsidian` 或中文「黑曜石」；机器人界面可能把英文 `Obsidian` 翻译成「黑曜石」显示，但规则针对的是描述正文里的宿主名。
- 若扫描结果仍指向旧 commit（例如 `6e689a1`）或旧 tag（例如 `0.8.7`），说明扫的是**修复前的快照**，不是当前 `main`；应改扫 `main` 分支，或 bump 版本后扫新 tag（例如 `0.8.8`）。
- 等主要问题清干净后，再一次性做：
  - 更新 `manifest.json` / `package.json` / `versions.json`
  - 创建对应 GitHub tag / release
  - 走正式提交或正式复检
- 正式可安装发布，仍然依赖 **GitHub release** 与 **`manifest.json.version` 一致**。

## 预览扫描是什么

这里说的“预览扫描”，指的是官方社区提交流程中提供的 **预检查入口**，适合在正式审核前先跑机器人检查。

它的价值是：

- 提前发现机器人会拦下的问题
- 减少正式提审后的来回修改
- 尽量少浪费版本号和 release 记录

这类扫描更像“官方同源自检”，**不等于插件已经正式通过审核，也不等于已经进入社区目录**。

## 三种预览扫描怎么用

以下名称来自官方社区页面在 2026-05-16 的当前界面。这个界面未来可能改名，但使用意图大体稳定。

### 1. `Preview branch scan`

最适合开发中反复检查。

建议用途：

- 你正在持续修改 `main` 分支
- 你希望扫一遍，改一遍，再扫一遍
- 你不想每次都新建 tag 或 release

推荐填写：

- 仓库：公开插件仓库
- 分支：通常填 `main`

这是当前阶段的首选。

### 2. `Preview tag scan`

适合检查某个“准发布版本”。

建议用途：

- 你已经准备了一个较稳定的版本
- 你想确认某个 tag 对应的状态
- 你希望预览更接近正式发布时的内容

不适合高频试错，因为每次新 tag 都会让版本管理更乱。

### 3. `Preview SHA scan`

适合精确检查某一个 commit。

建议用途：

- 你要锁定某个具体提交
- 你在排查“这次改动前后到底是谁引入了问题”
- 你不想依赖分支继续前进后的最新状态

它更适合定位问题，不是日常最省事的主流程。

## 当前仓库推荐流程

对这个仓库，长期最省事的做法是：

1. 先保持默认开发分支可用
2. 用 `Preview branch scan` 扫 `main`
3. 机器人报什么，就修什么
4. 修完后继续扫 `main`
5. 直到主要问题都清理干净
6. 最后再统一 bump 版本并发正式 release

一句话总结：**先反复扫分支，后一次性发版本。**

## 预览扫描阶段要不要改版本号

默认建议：**不要因为只是想复查机器人结果，就频繁改正式版本号。**

原因有三个：

- GitHub release 历史会被无意义试错污染
- `manifest.json` 版本号容易先跑到一个并未正式发布的版本
- 后续正式审核时，版本号、tag、release 可能互相对不上

更稳的做法是：

- 预览扫描阶段：保持当前已发布正式版本号不乱跳
- 真正准备提交时：再一次性升级到目标版本

## 正式提交和 release 的关系

这个关系必须分清，否则最容易混乱。

### 1. 正式提交插件

官方开发文档要求：

- 仓库根目录要有 `README.md`
- 仓库根目录要有 `LICENSE`
- 要有合法的 `manifest.json`
- 正式提交前要创建 GitHub release
- release 的 tag 必须与 `manifest.json.version` 一致
- release 资产至少包含：
  - `main.js`
  - `manifest.json`
  - `styles.css`（可选）

### 2. 正式复检 / 修复审核反馈

官方开发文档写的是：

- 修完审核意见后，更新 GitHub release
- 不要新开一个新的提交 PR

社区论坛补充确认过两点：

- 机器人会看 **仓库 `main` 分支** 的代码
- 想重新触发验证，通常是 **修改 PR 对应内容并等待几分钟**，或按机器人提示重新触发

因此，长期可以这样理解：

- **预览扫描**：优先服务于“反复查问题”
- **正式提审后的收口**：最终仍然会落到正式版本与 release 一致

## “只填信息，是不是以后都不用发新版本了？”

不是。

正确理解是：

- 只填预览扫描信息，通常足够拿到一轮或多轮机器人反馈
- 但这不等于以后正式审核都不需要新版本
- 当你真正要发布一个通过审核、用户可安装的正式版本时，仍然需要：
  - 合法的版本号
  - 对应 tag
  - 对应 GitHub release
  - 对应 release 附件

所以，“预览扫描”解决的是 **尽量少浪费版本号**，不是“以后彻底不需要版本发布”。

## 实操建议

### 推荐节奏

1. 本地改代码
2. 推送到公开仓库 `main`
3. 跑 `Preview branch scan`
4. 看机器人反馈
5. 继续修
6. 重复 2-5
7. 问题基本清掉后，再正式升级版本并发 release

### 不推荐节奏

1. 改一点点
2. bump 一次版本
3. 发一次 release
4. 又发现问题
5. 再 bump 一次

这样会很快把版本历史弄乱，而且很多 release 没有实际价值。

## 常见误区

### 误区 1：预览扫描通过 = 正式审核通过

不是。预览扫描只是说明机器人这一轮没有拦下明显问题，正式人工审核仍可能提出要求。

### 误区 2：机器人只看 release

不完整。根据官方论坛说明，机器人会看仓库 `main` 分支代码；而正式发布安装链路又依赖 release 资产。

### 误区 3：每修一个问题都该涨版本

不建议。至少在预览扫描阶段，不该这么做。

### 误区 4：复检要重新开一个新的 PR

官方文档明确说不要新开 PR，应该在原有提交链路上修复并等待复检。

## 每次预览扫描前的自查清单

- 仓库是公开可访问的
- `README.md` 在仓库根目录
- `LICENSE` 在仓库根目录
- `manifest.json` 在仓库根目录
- `manifest.json` 里的 `id`、`name`、`author`、`description` 与提交信息一致
- 没有把本地敏感文件、私钥、账号配置推上去
- 构建产物与提交说明一致
- 如果已经准备正式发布，确认 tag、release、版本号三者一致

## Release 资产硬规则

正式 release 时，默认只上传这三个资产：

- `main.js`
- `manifest.json`
- `styles.css`

不要把下面这些文件挂到 release 资产里：

- `versions.json`
- 测试报告
- 覆盖率文件
- 其他构建中间产物

原因很简单：

- Obsidian 社区安装链路只认三件套
- 多余文件会触发官方机器人 “额外文件” 提醒
- `versions.json` 应该留在仓库根目录，用于仓库兼容映射，不是安装资产

## GitHub 工件认证说明

当前仓库的发布工作流应当为以下 release 资产生成 GitHub artifact attestation：

- `main.js`
- `manifest.json`
- `styles.css`

如果机器人还提示“没有 GitHub 工件认证”，优先检查：

1. 这次 release 是否真的是通过 `.github/workflows/release.yml` 自动发布
2. 是否有人手动在 GitHub 页面补传或重传过资产
3. 当前 tag 对应的这次 release 是否早于工件认证工作流生效

最稳妥的做法是：

- 让 tag 触发自动 release workflow
- 由 workflow 直接构建、attest、上传三件套
- 不再手工追加额外 release 文件

### 历史 release 的特别说明

如果你在 Obsidian 社区后台看到：

- `The release asset does not have a GitHub artifact attestation`
- `The release contains additional files`

先不要误判成“当前仓库代码还没修”。

这两类提示经常来自 **已经发布出去的旧 release**：

- 旧 release 可能是在 attestation 工作流落地前发布的
- 旧 release 可能手工附加过 `sql-wasm.wasm`、`versions.json` 或其他额外文件

这种情况下，**本地代码修复不会反向修改 GitHub 上的旧 release**。正确收口方式是：

1. 保持当前仓库通过本地检查
2. 确认 `.github/workflows/release.yml` 仍只上传三件套
3. 用新 tag 重新触发自动 release
4. 不要在 GitHub 页面手工补传额外资产

只要新的正式 release 是由工作流自动构建、自动 attest、自动上传，历史 release 遗留的这两类提示就不会继续污染新版本审核。

## 对这个仓库的具体建议

当前最适合的策略是：

- 继续把 **`Preview branch scan`** 当成主要排错入口
- 只有在机器人主要问题已经清掉后，再推进正式版本发布
- 不要为了试一次机器人就频繁新增 `0.8.x` 小版本

如果将来官方社区页面的按钮名称变了，优先保留下面这个判断原则：

- 想反复试错：选“扫描分支最新代码”
- 想检查准发布版本：选“扫描 tag”
- 想检查某个固定提交：选“扫描 commit / SHA”
